= Creating a Gateway Site
:navtitle: Creating a Gateway Site

== Overview

A gateway site is a local system site on a Linux host that joins an existing application network.
This section walks through creating a site, linking it to an OpenShift cluster, and managing its lifecycle.

== Creating a Site Using the CLI

=== Step 1: Set the Platform and Install the Controller

[source,bash,role=execute]
----
export SKUPPER_PLATFORM=podman
skupper system install
----

For the `linux` (systemd) platform, skip the `skupper system install` step -- the `skupper-router` RPM provides the router directly.

=== Step 2: Create the Site

[source,bash,role=execute]
----
skupper site create my-local-site
----

.Expected output
----
Waiting for status...
Site "my-local-site" is ready.
----

The site is created but not yet running.

=== Step 3: Start the Site

[source,bash,role=execute]
----
skupper system start
----

This launches the router (as a Podman container, Docker container, or systemd service depending on the platform).

[NOTE]
====
As an alternative to the multi-step workflow above, you can use `skupper system setup` to install the controller, process all resource files, and start the site in a single command.
See <<declarative-resource-management>> below for details.
====

== Linking to an OpenShift Site

To join the application network, you create a link between the local system site and an OpenShift or Kubernetes site.
The Kubernetes site must have link access enabled.

=== Linking with a Token

. On the Kubernetes site, ensure link access is enabled and issue a token:
+
[source,bash,role=execute]
----
oc project site-west
skupper site update --enable-link-access
skupper token issue ~/local-site-token.yaml
----

. Copy the token file to the Linux host (e.g., via `scp`).

. On the Linux host, redeem the token:
+
[source,bash,role=execute]
----
skupper token redeem ~/local-site-token.yaml
----

. Verify the link:
+
[source,bash,role=execute]
----
skupper link status
----
+
You might need to run this command multiple times until the link is ready:
+
.Expected output
----
NAME                                          STATUS   COST   MESSAGE
west-<uuid>                                   Ready    1      OK
----

NOTE: In this release, the CLI does not support issuing tokens from local system sites.
You can redeem tokens on a local system site and create link resources.

=== Linking with a Link Resource

An alternative to tokens is to generate a link resource YAML file:

. On the Kubernetes site, ensure link access is enabled:
+
[source,bash,role=execute]
----
skupper site update --enable-link-access
----

. Generate a link resource file:
+
[source,bash,role=execute]
----
skupper link generate > ~/link-to-west.yaml
----

. On the Linux host, apply the link resource:
+
[source,bash,role=execute]
----
skupper system apply -f ~/link-to-west.yaml
----

. Verify the link:
+
[source,bash,role=execute]
----
skupper link status
----

== Site Bundles

Site bundles allow you to package an entire site configuration into a distributable `.tar.gz` file.
This is useful when deploying sites to remote Linux hosts where you do not want to install the full CLI.

=== Creating a Bundle

On a host with the CLI installed:

[source,bash,role=execute]
----
export SKUPPER_PLATFORM=podman
skupper system install
skupper site create remote-site
skupper system generate-bundle remote-site
----

.Expected output
----
Site "remote-site" has been created (as a distributable bundle)
Installation bundle available at: /home/user/.local/share/skupper/bundles/remote-site.tar.gz
Default namespace: default
Default platform: podman
----

=== Deploying a Bundle

. Transfer the bundle to the remote host:
+
[source,bash,role=execute]
----
scp /home/user/.local/share/skupper/bundles/remote-site.tar.gz user@remote-host:~/
----

. On the remote host, extract and install:
+
[source,bash,role=execute]
----
tar -xzvf remote-site.tar.gz
./install.sh
----
+
The site is now running.
You can verify with `skupper site status` if the CLI is installed on the remote host.

NOTE: The bundle includes all configuration files needed to run the site.
The CLI is not required on the remote host -- only the container runtime (Podman or Docker) or the `skupper-router` RPM (Linux platform).

== Declarative Resource Management

On local system sites, the CLI writes resource files to a directory on the local filesystem instead of submitting them to a Kubernetes API server.
You can also place resource files in this directory yourself, bypassing the CLI entirely.

=== Input Resources Directory

All resources for a given namespace are stored under:

----
~/.local/share/skupper/namespaces/<namespace>/input/resources/
----

The directory structure organizes resources by type:

----
~/.local/share/skupper/namespaces/default/input/resources/
├── sites/
│   └── my-site.yaml
├── connectors/
│   └── backend.yaml
├── listeners/
│   └── frontend.yaml
└── token.yaml              <-- access tokens are placed at the top level
----

When you run `skupper site create` or `skupper connector create`, the CLI writes YAML files into the appropriate subdirectories.
You can achieve the same result by writing the files directly.

=== Using `skupper system setup`

The `skupper system setup` command installs the controller (if needed), reads all resource files from the input directory, and starts the site in a single step:

[source,bash,role=execute]
----
skupper system setup
----

.Expected output
----
Sources will be consumed from the namespace "default"
Site "my-site" has been created on namespace "default"
Platform: podman
Definition is available at: /home/user/.local/share/skupper/namespaces/default/input/resources
----

This is equivalent to running `skupper system install`, `skupper site create`, and `skupper system start` separately.

=== Example: Declarative Workflow

This example creates a site, connector, and link entirely through file placement:

. Write a site definition:
+
[source,bash,role=execute]
----
mkdir -p ~/.local/share/skupper/namespaces/default/input/resources/sites
cat > ~/.local/share/skupper/namespaces/default/input/resources/sites/my-site.yaml <<EOF
apiVersion: skupper.io/v2alpha1
kind: Site
metadata:
  name: my-site
spec: {}
EOF
----

. Write a connector definition:
+
[source,bash,role=execute]
----
mkdir -p ~/.local/share/skupper/namespaces/default/input/resources/connectors
cat > ~/.local/share/skupper/namespaces/default/input/resources/connectors/backend.yaml <<EOF
apiVersion: skupper.io/v2alpha1
kind: Connector
metadata:
  name: backend
spec:
  routingKey: backend
  port: 8080
  host: localhost
EOF
----

. Copy a token file into the resources directory:
+
[source,bash,role=execute]
----
cp ~/my-token.yaml ~/.local/share/skupper/namespaces/default/input/resources/
----

. Start everything with a single command:
+
[source,bash,role=execute]
----
skupper system setup
----

This approach is useful for automation, scripting, and scenarios where you want to pre-stage all configuration before starting the site.

[NOTE]
====
To apply changes after the site is already running, use `skupper system reload` instead of `skupper system setup`.
====

== Lifecycle Management

=== Applying Configuration Changes

After modifying site configuration (adding connectors, listeners, or links), apply changes with:

[source,bash,role=execute]
----
skupper system reload
----

=== Stopping and Starting

[source,bash,role=execute]
----
skupper system stop
skupper system start
----

=== Deleting a Site

[source,bash,role=execute]
----
skupper site delete <site-name>
skupper system stop
----

=== Uninstalling the Controller

After deleting all sites, you can remove the controller:

[source,bash,role=execute]
----
skupper system uninstall
----
