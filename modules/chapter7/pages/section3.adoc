= Edge Computing and IoT
:navtitle: Edge Computing and IoT

== Edge Computing Overview

Edge computing moves application workloads closer to where data is generated and consumed — retail stores, factory floors, hospitals, cell towers, or remote facilities.
This reduces latency, conserves bandwidth, and enables applications to function even when connectivity to the central data center is intermittent.

Red Hat Service Interconnect is well-suited for edge scenarios because:

* **No inbound ports required** — Edge sites initiate outbound connections to hub sites, which is compatible with the restrictive firewall policies common at edge locations
* **Lightweight footprint** — Service Interconnect runs a single router container per site, making it feasible on resource-constrained edge hardware
* **Resilience to disconnection** — Sites operate independently when links are down, and traffic resumes automatically when connectivity is restored
* **Local system sites** — Non-Kubernetes workloads on Linux systems can participate in the application network, which is common at edge locations where full Kubernetes clusters may not be available

== Edge Topology Patterns

=== Hub-to-Edge

The most common edge pattern.
A central hub cluster (in the cloud or data center) connects to many edge sites.
Edge sites run local services and report data back to the hub.

----
                +-------------------+
                |    Hub Cluster    |
                | (cloud/DC)       |
                |  aggregation-svc |
                |  dashboard       |
                +--------+--------+
                   / | | | \
                  /  | | |  \
    +------+ +------+ +------+ +------+ +------+
    |Edge 1| |Edge 2| |Edge 3| |Edge 4| |Edge 5|
    |sensor| |sensor| |sensor| |sensor| |sensor|
    +------+ +------+ +------+ +------+ +------+
----

Each edge site:

* Creates a local site (Kubernetes namespace or local system site on Linux)
* Links to the hub site using an access token
* Exposes local services (sensors, data collectors) via connectors
* Consumes central services (configuration, updates) via listeners

=== Regional Aggregation

For deployments with many edge sites, add regional aggregation layers to reduce the number of direct connections to the central hub.

----
    +-------------------+
    |   Central Hub     |
    +--------+----------+
            / \
           /   \
    +-----+--+ +--+-----+
    |Region A| |Region B|
    +---+----+ +----+---+
       / \         / \
      /   \       /   \
    E1    E2    E3    E4
----

Regional sites aggregate data from local edge sites and forward it to the central hub.
This reduces the number of links the central hub must manage and keeps regional traffic local.

== Considerations for Edge Deployments

=== Bandwidth Constraints

Edge locations often have limited network bandwidth.
Service Interconnect operates at Layer 7 and only transmits application-level traffic — there is no overhead from VPN tunnels or network-level encapsulation.

To further manage bandwidth:

* **Expose only needed services** — Only create connectors and listeners for services that genuinely need cross-site access
* **Use link cost** — Set higher costs on links to edge sites so that traffic prefers local services when available
* **Consider data aggregation** — Process and aggregate data at the edge before sending summaries to the hub

=== Intermittent Connectivity

Edge sites may experience network interruptions.
Service Interconnect handles this gracefully:

* Links reconnect automatically when connectivity is restored
* Sites continue to operate independently during disconnection
* Local services remain available to local consumers
* No data loss in the application network itself (though application-level data buffering is the responsibility of the application)

=== Resource Constraints

Edge hardware may have limited CPU and memory.
Service Interconnect's resource requirements at the edge are modest:

* The router container typically requires 128-256 MB of memory and minimal CPU
* On Linux systems, the `skupper-router` process runs as a systemd service with a similarly small footprint
* No additional control plane components are needed at the edge — the operator runs on the hub cluster

=== Security at the Edge

Edge locations present unique security challenges — physical access to hardware, untrusted networks, and limited security infrastructure.

Service Interconnect mitigates these risks:

* **mTLS on all links** — Traffic between edge and hub is always encrypted and authenticated
* **No stored credentials** — After token redemption, the token is invalidated. The certificate is the ongoing credential, and it is stored in the site's namespace (or local filesystem for local system sites)
* **Outbound-only connections** — Edge sites do not need to accept inbound connections, reducing the attack surface
* **Per-site isolation** — Compromising one edge site does not grant access to other sites in the network

=== Scaling to Many Edge Sites

When deploying to hundreds or thousands of edge sites, consider:

* **Multi-use access tokens** — Issue tokens with `--redemptions-allowed` set to the number of edge sites that will link to a hub, reducing the number of token issue operations
* **Site bundles** — Use `skupper system generate-bundle` to create distributable packages that can be deployed to edge sites without manual CLI interaction
* **Automation** — Integrate site creation and linking into your edge provisioning pipeline (Ansible, RHEL Image Builder, MicroShift)
* **Regional hubs** — Use the regional aggregation pattern to limit the number of links per hub site

== Edge Platforms

Service Interconnect supports several deployment models at the edge:

[cols="1,2,1",options="header"]
|===
|Platform |Description |Use Case

|**OpenShift (full)**
|Full OpenShift cluster at the edge
|Large edge sites with multiple applications

|**MicroShift**
|Lightweight OpenShift on edge devices
|Single-node edge devices with Kubernetes API

|**Local system site (Podman)**
|Skupper router in a Podman container on Linux
|Linux servers or VMs without Kubernetes

|**Local system site (systemd)**
|Skupper router as a systemd service on Linux
|Bare-metal Linux systems, appliances
|===

All of these platforms participate in the same application network using the same linking and service exposure mechanisms.
The choice of platform depends on the hardware capabilities and management requirements of the edge location.
