Troubleshooting

General Diagnostic Commands

These commands help you quickly assess the state of your Service Interconnect deployment.

Check Site Status

oc get site -n <namespace>
Healthy output
NAME        STATUS   SITES IN NETWORK   MESSAGE
site-west   Ready    2                  OK

If STATUS is not Ready, check the operator logs (see below).

Check All Service Interconnect Resources

oc get site,link,connector,listener,accessgrant,accesstoken -n <namespace>

Check Operator Logs

oc logs deployment/skupper-controller -n <namespace>

Check Router Logs

oc logs deployment/skupper-router -n <namespace>

Common Issues

Site Not Becoming Ready

Symptom: oc get site shows Pending or no status.

Possible causes:

  1. Operator not installed — Verify the Service Interconnect operator is installed and running:

    oc get csv -A | grep skupper

    Look for Succeeded in the output.

  2. Operator not watching namespace — If the operator is installed in a single namespace, ensure it matches the site’s namespace. For AllNamespaces mode, the operator should be in openshift-operators.

  3. Resource limits — The operator or router may be unable to schedule due to resource constraints:

    oc get events -n <namespace> --sort-by='.lastTimestamp'

Link Not Becoming Ready

Symptom: skupper link status shows Pending or Not Operational.

Possible causes:

  1. Token expired — Tokens expire after 15 minutes by default. Issue a new token and redeem it.

  2. Token already used — Tokens are single-use by default. Issue a new token.

  3. Network connectivity — The linking site must be able to reach the token-issuing site on the link access endpoint (typically port 443 via an OpenShift route or LoadBalancer). Check:

    oc get route -n <namespace> | grep skupper

  4. Link access not enabled — The site that issued the token must have link access enabled:

    skupper site update --enable-link-access

  5. DNS resolution — The linking site must be able to resolve the hostname in the token. Verify from the linking site:

    nslookup <hostname-from-token>

Diagnostic steps:

oc get link -n <namespace> -o yaml

Look at the status.conditions field for error messages.

Listener Shows "No Matching Connector"

Symptom: skupper listener status shows MATCHING-CONNECTOR: false.

Possible causes:

  1. Routing key mismatch — The listener and connector must use the same routing key. Check both:

    oc get listener -n <namespace> -o yaml | grep routingKey
oc get connector -n <namespace> -o yaml | grep routingKey

  2. Connector not ready — The connector’s target workload may not be running:

    skupper connector status

  3. Sites not linked — The listener and connector are on different sites, but the sites are not linked:

    skupper link status

Service Not Reachable Through the Application Network

Symptom: Requests to a listener service time out or return connection errors.

Diagnostic steps:

  1. Verify the listener exists and has a matching connector:

    skupper listener status

  2. Verify the Kubernetes service was created:

    oc get service <listener-name> -n <namespace>

  3. Verify the connector’s target workload is running and listening on the correct port:

    oc get pods -n <connector-namespace> -l <workload-selector>

  4. Check the router logs for errors:

    oc logs deployment/skupper-router -n <namespace> | tail -50

  5. Test connectivity directly to the workload (bypassing Service Interconnect):

    oc exec -n <connector-namespace> deployment/<workload> -- curl -s http://localhost:<port>

Certificate-Related Errors

Symptom: Links fail with TLS errors, or router logs show certificate verification failures.

Possible causes:

  1. Corrupted or missing certificate Secrets — Check that all certificate Secrets exist:

    oc get secrets -n <namespace> | grep skupper

    You should see skupper-local-ca, skupper-site-ca, skupper-service-ca, and skupper-site-server.

  2. Clock skew — Certificate validation is time-sensitive. Ensure system clocks are synchronized across all sites.

  3. Regenerate certificates — Delete the server certificate and let the operator regenerate it:

    oc delete secret skupper-site-server -n <namespace>
    Do not delete the CA Secrets unless you intend to re-establish all links.

Network Observer Not Starting

Symptom: The NetworkObserver pod is not running or is in CrashLoopBackOff.

Diagnostic steps:

  1. Check if the Network Observer operator is installed:

    oc get csv -A | grep network-observer

  2. Check the pod events:

    oc get events -n <namespace> --sort-by='.lastTimestamp' | grep network-observer

  3. Check pod logs:

    oc logs -n <namespace> -l app.kubernetes.io/component=network-observer

  4. Verify resource availability — the Network Observer may need more memory:

    oc describe pod -n <namespace> -l app.kubernetes.io/component=network-observer

Local System Site Issues

Symptom: skupper site status fails or shows errors on a Linux system.

Diagnostic steps:

  1. Verify the platform is set correctly:

    echo $SKUPPER_PLATFORM

  2. For Podman platform, verify the Podman socket is active:

    systemctl --user status podman.socket

  3. For Linux (systemd) platform, verify the router service:

    systemctl --user status skupper-router

  4. Check for lingering enabled (required for Podman sites to persist across logouts):

    loginctl show-user $(whoami) | grep Linger

  5. Reload after configuration changes:

    skupper system reload

Getting Support

If you cannot resolve an issue using the steps above:

  1. Collect diagnostic information:

    skupper version
oc get site,link,connector,listener -n <namespace> -o yaml
oc logs deployment/skupper-router -n <namespace> > router-logs.txt
oc logs deployment/skupper-controller -n <namespace> > controller-logs.txt

  2. Open a support case with Red Hat, including the collected diagnostic data.
