Lab Environment

Overview

This course requires you to work with multiple Service Interconnect sites. You can complete the labs using one of two environment options:

Option Requirements Best For

Option A: Two OpenShift Clusters

Two OpenShift Container Platform 4.20 clusters

Realistic multi-cluster experience; demonstrates cross-network connectivity

Option B: Single Cluster with Namespaces

One OpenShift Container Platform 4.20 cluster

Quick setup; all SI concepts work identically at the namespace level

Red Hat Service Interconnect operates at the namespace level — each site is initialized within a namespace. This means you can simulate a multi-cluster environment by creating separate namespaces on a single cluster. All core concepts (sites, tokens, links, exposing services) work the same way in both options.

Option B does not demonstrate cross-network connectivity, since both namespaces share the same cluster network. For production scenarios and Chapter 5 (Local System Sites), Option A with a separate Linux system is required.

Option A: Two OpenShift Clusters

Lab Architecture

  • Cluster A (site-west) — runs frontend services

  • Cluster B (site-east) — runs backend services (database, API)

  • RHEL 9 VM (gateway-host) — used in Chapter 5 for non-Kubernetes workloads (optional)

Instructions to Launch Your Lab on the Red Hat Demo Platform (RHDP)

  1. Log in to the RHDP portal

  2. Search for the catalog entry: Red Hat Service Interconnect Lab

  3. Click on the catalog entry in the search results

  4. On the catalog page, click the Order button

  5. Fill out the required details in the order form

  6. Review the warning at the bottom of the form and check the box labeled:
    "I confirm that I understand the above warnings."

  7. Click the Order button to place your lab order

Important Notes

  • This lab may take approximately 30-45 minutes to become ready

  • You will receive an email with access details once your lab environment is ready

  • You can also retrieve lab access directly from the RHDP portal

How to Access Your Lab via the RHDP Portal

  1. On the RHDP portal, click on the Services option in the left-hand menu

  2. Select your lab from the listings on the right-hand side of the page to view access details

Verify Lab Access

Log in to both clusters using the oc CLI:

oc login --server=<cluster-a-api-url> -u <username> -p <password>
oc login --server=<cluster-b-api-url> -u <username> -p <password>

If your lab includes a RHEL 9 VM, verify SSH access:

ssh <username>@<gateway-host>

Option B: Single Cluster with Namespaces

Lab Architecture

On a single OpenShift 4.20 cluster, create two namespaces to simulate separate sites:

  • Namespace site-west — runs frontend services

  • Namespace site-east — runs backend services (database, API)

Setup

Log in to your OpenShift cluster:

oc login --server=<cluster-api-url> -u <username> -p <password>

Create the two namespaces:

oc new-project site-west
oc new-project site-east

Set the Pod Security Admission warning level to baseline on both namespaces:

oc label namespace site-west pod-security.kubernetes.io/warn=baseline --overwrite
oc label namespace site-east pod-security.kubernetes.io/warn=baseline --overwrite

By default, OpenShift namespaces use the restricted Pod Security profile for warnings. This causes harmless warning messages when running ad-hoc pods with oc run (e.g., for testing connectivity), because the default container security context does not explicitly set allowPrivilegeEscalation: false. Setting the warning level to baseline suppresses these warnings without changing the enforcement policy — pods that would actually violate security constraints are still rejected.

Using Two Namespaces as Separate Sites

Throughout this course, when instructions refer to "Cluster A" or site-west, work in the site-west namespace:

oc project site-west

When instructions refer to "Cluster B" or site-east, switch to the site-east namespace:

oc project site-east
You can use two terminal windows — one set to each namespace — to make switching easier.
Chapter 5 (Local System Sites) requires a separate Linux system and cannot be completed with the single-cluster option alone.
