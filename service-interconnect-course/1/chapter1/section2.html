Architecture and Key Concepts

The Application Network

Service Interconnect creates an application network — a virtual network that connects application services across distributed sites. Unlike traditional networks that route IP packets, the application network routes messages between service endpoints at Layer 7.

From an application’s perspective, remote services appear as local services within the same namespace. The application connects to a local endpoint, and Service Interconnect transparently routes the traffic to the actual service, wherever it runs.

Core Concepts

Sites

A site is a location where Service Interconnect is installed and running. On Kubernetes or OpenShift, a site corresponds to a namespace. On Linux (RHEL), a site runs as a set of containers managed by Podman or as a systemd service.

Each site runs one or more Service Interconnect routers that participate in the application network.

You create a site using the Site custom resource:

apiVersion: skupper.io/v2alpha1
kind: Site
metadata:
  name: site-west
  namespace: site-west
spec: {}

To enable link access on a site (allowing other sites to link to it), set the linkAccess field:

apiVersion: skupper.io/v2alpha1
kind: Site
metadata:
  name: site-west
  namespace: site-west
spec:
  linkAccess: default

Routers

Routers are the core infrastructure of the application network. They are lightweight processes deployed automatically when a site is created.

Routers perform Layer 7 message routing — they do not forward raw IP packets. Instead, they route application-level messages between listeners and connectors based on routing keys.

All router-to-router connections are encrypted with mutual TLS using a private certificate authority.

Links

A link is a connection between two sites that allows their routers to exchange traffic. Links are established using outbound connections only — no inbound firewall rules are required at either site.

To create a link, one site generates an access token (or access grant), and the other site uses that token to establish the connection.

Access Tokens and Access Grants

Access grants and access tokens are the mechanisms for authorizing site-to-site connections.

An AccessGrant is a permission on a listening site that allows redemption of access tokens to create links. The component it gives permission to is the GrantServer, which is an HTTPS server that ultimately sets up the link. It defines how many times the grant can be redeemed and when it expires:

apiVersion: skupper.io/v2alpha1
kind: AccessGrant
metadata:
  name: grant-west
  namespace: site-west
spec:
  redemptionsAllowed: 2   (1)
  expirationWindow: 25m   (2)
1 Number of times the grant can be redeemed (default: 1)
2 How long the grant remains valid (default: 15m)

An AccessToken is a short-lived, usually single-use credential that contains the AccessGrant URL, a secret code, and a certificate. A connecting site redeems this token for a Link resource to establish a link to the listening site:

apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-to-west
  namespace: site-east
spec:
  code: "<secret-code>"
  ca: "<ca-certificate>"
  url: "<grant-server-url>"
Access to this file provides access to the application network. Protect it appropriately.

Connectors

A connector binds a local workload to the application network, making it available to remote sites. You create a connector on the site where the actual service is running.

A connector specifies:

  • The local workload to expose (via a selector or host)

  • A routing key that identifies the service on the application network

  • The port the workload is listening on

apiVersion: skupper.io/v2alpha1
kind: Connector
metadata:
  name: backend
  namespace: site-east
spec:
  routingKey: backend
  port: 8080
  selector: app=backend

Listeners

A listener creates a local service endpoint that forwards traffic to remote connectors. You create a listener on the site where you want to consume the service.

A listener specifies:

  • A routing key that must match the connector’s routing key

  • The local port to listen on

  • The hostname for the local service

apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: backend
  namespace: site-west
spec:
  routingKey: backend
  port: 8080
  host: backend

When a listener is created, Service Interconnect automatically creates a Kubernetes service in the local namespace. Applications connect to this local service as they would any other service — the routing to the remote workload is handled transparently.

Routing Keys

A routing key is a string that matches listeners with connectors across the application network. When a listener and a connector share the same routing key, traffic sent to the listener is routed to the connector’s workload.

Multiple connectors can share the same routing key, enabling load balancing across sites.

Routing Patterns

Service Interconnect supports two routing patterns that control how traffic is distributed when multiple connectors share the same routing key:

Anycast (default)

Routes each connection or request to one destination. Two algorithms are available:

  • balanced — distributes active TCP connections evenly across all connectors with the same routing key, regardless of site location.

  • closest — routes to the connector with the lowest total link cost. Local workloads (same site) have a cost of 0; remote workloads are reached via links whose costs are summed along the path. This is useful when you want to prefer local processing and only fail over to remote sites.

Multicast

Routes each connection or request to all destinations that share the same routing key. Every connector receives a copy of the traffic. This is useful for scenarios like fan-out notifications or parallel processing.

You configure the routing pattern using the routingMode field on a Listener or Connector resource:

apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: backend
spec:
  routingKey: backend
  port: 8080
  routingMode: anycast  (1)
1 Valid values: anycast (default) or multicast.

Link Cost

Every link between sites has a cost value (default 1). The router uses cost to determine the preferred path when multiple routes exist to the same routing key. Local workloads (connectors in the same site as the listener) have an implicit cost of 0.

Lower total path cost is preferred. For example, if site-west has a link to site-east with cost 1 and a link to site-central with cost 5, traffic from site-west prefers site-east when using the closest anycast algorithm.

Set the cost when creating a link by specifying it during token redemption or in the Link resource YAML:

apiVersion: skupper.io/v2alpha1
kind: Link
metadata:
  name: link-to-east
spec:
  cost: 1  (1)
1 Higher values make a link less preferred. Use high values like 9999 to create failover-only paths.
Load balancing in Service Interconnect balances active TCP connections, not individual HTTP requests. A new TCP connection is assigned to a destination based on the current distribution of active connections. This is different from round-robin or request-level load balancing.

How Traffic Flows

The following diagram illustrates how a frontend application in site-west connects to a backend service in site-east:

site-west (namespace)              site-east (namespace)
┌─────────────────────┐            ┌─────────────────────┐
│                     │            │                     │
│  frontend pod       │            │  backend pod        │
│    │                │            │    ▲                │
│    ▼                │            │    │                │
│  listener           │            │  connector          │
│  (routing key:      │            │  (routing key:      │
│   "backend")        │            │   "backend")        │
│    │                │            │    ▲                │
│    ▼                │            │    │                │
│  SI router ─────────┼── mTLS ────┼── SI router         │
│                     │  (link)    │                     │
└─────────────────────┘            └─────────────────────┘

  1. The frontend pod connects to the local backend service (created by the listener) on port 8080.

  2. The listener receives the connection and forwards it to the local SI router.

  3. The SI router in site-west routes the message over the link to the SI router in site-east, using mutual TLS encryption.

  4. The SI router in site-east delivers the message to the connector.

  5. The connector forwards the connection to the backend pod.

The frontend application has no awareness that the backend is running in a different site. It simply connects to a local service endpoint.

Custom Resources Summary

Service Interconnect 2.1 uses the following custom resources (CRDs):

Resource Purpose

Site

Defines a Service Interconnect site in a namespace

Listener

Creates a local service endpoint that routes to remote connectors

Connector

Exposes a local workload to the application network

AccessGrant

Authorizes remote sites to create links (server side)

AccessToken

Redeems an access grant to establish a link (client side)

Link

Represents an active connection between two sites

All resources use the skupper.io/v2alpha1 API group.
